# SI Hazard-Warning System — Repository Audit

**Date:** 2026-09-22
**Scope:** Read-only analysis of the repository as it stands after the system-composition stage (commit `ec00fae`). No features added or scope expanded. Baseline verified before analysis: `npx vitest run` → **136/136 tests passing** across 22 test files; `npm audit` → **0 vulnerabilities**.

**How to read this report:** findings are grouped by severity, not by file. Two full mappings requested separately (acceptance-criteria coverage, threat-model spot check) are included as their own reference sections near the end. Nothing in `src/` was changed to produce this report — see the one exception noted under H4, which is reported, not fixed.

---

## Summary

Five things were asked for: (1) cross-check every prior flag against current reality, (2) find genuine duplication, (3) find dead/orphaned code, (4) map tests against the doc's 12 acceptance criteria, (5) spot-check the threat model. Headline results:

- Most prior flags **held up** — they're still true, still where they were left, still isolated to their original scope. Listed in [Confirmed-accurate flags](#confirmed-accurate-flags-no-action-needed).
- One flag has **genuinely drifted**: `NotificationService.send()`'s own doc comment claims no orchestrator exists to wire approvals into sends — untrue since `ApprovedSend.js` was built two stages ago (H4).
- Two acceptance criteria (**#2** malformed/untrusted input, **#11** stale-source detection) have **no implementation and no tests** — not just undertested, genuinely unbuilt.
- The **spoofed/untrusted source feed** threat is entirely unmitigated in code today — trust in the SIMS feed is implicit in a configured URL, nothing more.
- Duplication found is minor and mostly low-risk to consolidate (a validation loop repeated 5 times byte-for-byte); nothing suggests the module boundaries themselves are wrong.
- Two small pieces of genuinely dead code were found (`tierFor()`, unused-outside-its-own-test `resolveEnvironmentModeFromEnv()`), plus one intentionally-orphaned scaffold (`sourceHierarchy.js`) that's still honestly labeled as such.

## High-severity findings

### H1. Acceptance criterion #2 ("malformed or untrusted input is rejected or quarantined") has no implementation and no test

`SIMSCAPAdapter.fetchAlerts()` (`src/ingestion/SIMSCAPAdapter.js:32-39`) loops over RSS items and calls `fetchAlert()` for each with **no per-item try/catch**. `parseCapXml()` (`src/shared/capParser.js:60-65`) does throw on a non-CAP document, but that throw propagates straight out of `fetchAlerts()` and aborts the entire batch — one malformed item currently takes down every other alert in the same poll. There is no "quarantine" concept anywhere (no place a rejected item is stored/logged for later inspection instead of just failing the request).

No test anywhere constructs malformed/garbage XML and asserts on the result. `tests/ingestion/SIMSCAPAdapter.live.test.js` only exercises the real, well-formed live feed.

This is both a design gap (nothing isolates one bad item from the rest of a poll) and a coverage gap (zero tests either way). Recommend deciding: should a malformed item be skipped-and-logged, quarantined-for-review, or should the whole poll legitimately fail loudly? Then build + test whichever is chosen.

### H2. Acceptance criterion #11 ("stale source data produces a SOURCE INTERRUPTION state") does not exist in any form

Confirmed via full-repo search: no `SOURCE_INTERRUPTION` state, no health/staleness tracking on `HazardSource` or `SIMSCAPAdapter`, nothing in `HazardWarningSystem.ingestAndProcess()` that distinguishes "the feed returned zero items because there's genuinely no active warning" from "the feed returned zero items because it's down/unreachable/erroring." This is a real gap between "no warning" and "we don't know" — exactly the failure mode the doc's threat model calls out ("a source outage misread as 'no warning'"). Nothing was ever built for this in any prior stage; it isn't a case of insufficient testing, the feature itself doesn't exist.

### H3. Threat: "spoofed or untrusted source feed" is unmitigated in code

`SIMSCAPAdapter` fetches whatever URL it's configured with (`DEFAULT_RSS_URL` or a constructor override) over plain `fetch`, with no signature verification, no sender authentication, no allowlist beyond "whatever URL you passed in," and no check that a CAP payload's `sender` field is the expected SIMS address before treating it as authoritative (`authoritative_for_local_warning: true` is set unconditionally in `SIMSCAPAdapter.fetchAlert()`, `src/ingestion/SIMSCAPAdapter.js:67`). `payload_hash` gives integrity/audit value (you can tell later if a payload was altered after capture) but — as the doc itself says — hashing doesn't authenticate the source. Anyone who can get a URL fetched by this adapter (DNS compromise, a MITM on a misconfigured `fetchImpl`, a compromised S3 bucket) can currently inject an "authoritative" alert with no code-level check catching it. This is the same root gap as H1/H2 — the ingestion boundary has no defense beyond "trust the transport."

### H4. Stale, now-false comment in `NotificationService.send()`'s own JSDoc — confirmed drift

`src/distribution/NotificationService.js:90-94` still reads:

> "Wiring an approved ApprovalWorkflow request's outcome through to an actual NotificationService.send() call is left to whatever future caller orchestrates the two — not built here, since **no such orchestrator exists yet in this codebase.**"

This was true when written (the "distribution layer core" stage) but has been false since `src/governance/ApprovedSend.js` was built — that orchestrator has existed for two full stages, is tested (`tests/governance/approvedSend.test.js`), and is the entry point `HazardWarningSystem.sendApproved()` itself delegates to. The **class-level** docstring a few lines above (`NotificationService.js:44-63`) is accurate and correctly references `ApprovedSend.js` by name — only this one method-level paragraph was never updated when the orchestrator landed. This is exactly the "silently drifted, contradicted by later code" pattern the audit was asked to catch: a correct design decision, described accurately in one place and incorrectly in another, in the same file. **Not fixed** — reported for a decision, per the audit's own ground rules; it's a one-line, zero-risk comment edit whenever you want it done.

## Medium-severity findings

### M1. The `{recipientId, phoneNumber}` recipient shape is still informal, and its original justification is now stale

Every other cross-module contract in this codebase (`Alert`, `AdministrativeUnit`, `OutboundMessage`, `Subscriber`, `User`) is a validated domain model: `createX(fields)` + a `REQUIRED_FIELDS` array + `Object.freeze`. The recipient shape that flows from `src/subscribers/matching.js`'s `toRecipient()` through `NotificationService.send()`, `ApprovedSend.sendApproved()`, and `HazardWarningSystem` is just a repeated JSDoc annotation (`{ recipientId: string, phoneNumber: string }`) in five places, with **no factory and no runtime validation anywhere** — nothing stops an empty string, `undefined`, or a malformed phone number from reaching `provider.send()`.

When this shape was first introduced (distribution stage), it was reasonably flagged as provisional because subscriber management didn't exist yet. Subscriber management has existed for three stages now and produces exactly this shape via `toRecipient()` — the original "it's provisional" reasoning no longer applies, but the shape was never promoted to a real, validated model. This is a genuine inconsistency with the codebase's own established convention, not a design decision anyone actually made.

### M2. `REQUIRED_FIELDS` validation loop is duplicated byte-for-byte across 5 files

Identical logic in `src/normalization/Alert.js:73-76`, `src/geo/AdministrativeUnit.js:41-44`, `src/distribution/OutboundMessage.js:45-48`, `src/governance/Role.js:41-44`, `src/subscribers/Subscriber.js:91-94` — only the error message's type name differs between copies:

```js
for (const key of REQUIRED_FIELDS) {
  if (fields[key] === undefined || fields[key] === null) {
    throw new Error(`<TypeName> is missing required field: ${key}`);
  }
}
```

Low-risk, high-value consolidation candidate: a single `assertRequiredFields(fields, REQUIRED_FIELDS, typeName)` helper in `src/shared/`. This does not conflict with the doc's module-boundary intent — the *models* should stay separate, only this shared validation mechanics is duplicated.

### M3. Enum-membership validation duplicated 4 times

`Object.values(X).includes(fields.Y)` appears in `src/governance/Role.js:46` (role), `src/subscribers/Subscriber.js:96,99` (consent_status, status), `src/distribution/OutboundMessage.js:50` (status). Same shape as M2, smaller scale — could be folded into the same shared helper (`assertEnumMember(value, EnumObject, fieldName)`).

### M4. `ApprovedSend.sendApproved()`'s `expectedProfileId` is entirely caller-asserted, and this limitation isn't written down anywhere in the code

`sendApproved()` checks that an approval request's `profileId` equals whatever `expectedProfileId` the caller passes in (`src/governance/ApprovedSend.js:113`) — but nothing independently verifies that `expectedProfileId` is actually the right profile for how the message was constructed. `messageConstruction.js`'s `ConstructedMessage` carries no "how was this authored" field (templated official relay vs. transformed/localized vs. hand-typed emergency text), so there is no way for `sendApproved()` to check the caller's claim against the message itself. A caller could pass `TRUSTED_OFFICIAL_RELAY` for a hand-authored message and nothing in the code would catch it — only a correctly-behaving caller keeps this honest.

This exact gap was discussed out loud when `ApprovedSend.js` was built, but **it was never written into the code as a comment** — searched `src/` for "manually authored", "authorship", "expectedProfileId" together with any caveat language, and found none. Anyone reading only the source (not this conversation's history) would not learn about this limitation. Recommend at minimum adding the caveat as a code comment even before deciding whether to build a real fix.

### M5. Boundary-dataset `geometry_hash` is recorded but never verified — "corrupted boundary dataset" is detectable in hindsight only, not prevented

`boundaryDataset.js` computes and stores `geometry_hash` (`src/geo/boundaryDataset.js:93,95`) as provenance, and `mapping.js` threads it through into every mapping result (`src/geo/mapping.js:113-119`) for later replay/audit. But nothing anywhere compares that hash against a known-good value at load time — there's no "this file should hash to X, refuse to load if it doesn't" check. If the bundled GeoJSON were corrupted or tampered with, `loadBoundaryDataset()` would load it and compute a hash for whatever it found, with no built-in signal that anything was wrong. This is provenance for later forensic comparison, not an active integrity gate — worth being precise about which one it actually is, since the doc's threat model asks for a *control*, not just an audit trail.

### M6. "Stolen SMS/API credential" threat: correctly not-yet-applicable, but zero preparatory scaffolding exists

There is no real gateway account (`MockSMSProvider` has no credentials to steal), so this threat genuinely isn't live yet — but there's also no secret-management pattern anywhere in the codebase in preparation for when `BudgetSMSProvider` (or similar) is eventually built. Not a defect today; worth flagging so it isn't forgotten when a real provider is added — that's the point at which this threat becomes real and needs an actual control, not just a mock with nothing to steal.

### M7. Acceptance criterion #12 ("a historical event can be replayed deterministically") — the pipeline's *outcome* is deterministic, the *artifact* is not

The TC Maila replay's routing and dedup results are stable run-to-run (21 warnings → 1 event_id, same five ground-truth provinces, every run) — that part is genuinely deterministic. But `tests/replay/output/tc-maila-replay-report.md` regenerates with small diffs on every run (per-stage latency numbers, timestamps) because the harness measures real wall-clock time and calls `Date.now()`/`performance.now()` live rather than against a fixed clock. This has been treated as "expected churn" in every prior session, which is a reasonable call — but the nuance (logic is deterministic; the generated report's numbers aren't) isn't stated anywhere in `tests/replay/report.js` or `runReplay.js` itself. Someone reading criterion #12 literally, then reading only the code, would not learn that "deterministic" has this asterisk.

## Low-severity findings

### L1. `src/normalization/sourceHierarchy.js` — confirmed still accurate, still correctly self-documented, still completely unreachable

Its own module comment (`sourceHierarchy.js:1-23`) still honestly says it's a scaffold, not wired to anything, because the cross-source event-grouping it depends on doesn't exist. Verified via full-repo search: `compareSourceReadings` is imported **only** by its own test file — not by `DedupService`, not by `HazardWarningSystem`, not by anything else, even now that `HazardWarningSystem` exists as a natural place it could have been wired in. No drift here — the flag is exactly as accurate as when it was written — but worth a decision: build the missing cross-source grouping, wire this in some other way, or consciously accept it stays scaffold-only through the pilot.

### L2. `EnvironmentMode.resolveEnvironmentModeFromEnv()` is dead outside its own test

Exported and unit-tested (`tests/governance/environmentMode.test.js`), but never called by `HazardWarningSystem` or anything else in `src/` — every real construction path passes `environmentMode` as an explicit literal, never reads it from `process.env`. Either wire this into the actual composition root (so the "no silent default" guarantee applies to how the system is actually started, not just to a function nobody calls) or remove it.

### L3. `lifecycle.js`'s `tierFor()` is genuinely dead code

Defined, exported (`src/normalization/lifecycle.js:36-38,129`), and has **zero callers anywhere in the repository** — not from other code, not even from its own test file. `deriveLifecycleTransition()` never calls it either; a brand-new alert always classifies as `NEW` regardless of severity (`lifecycle.js:106-108`), so the WATCH-vs-WARNING tier distinction `tierFor` computes is currently unused by the state machine it appears to have been built for. Either wire it in (e.g., surface the tier on the transition result) or remove it.

### L4. Store-pattern duplication between `OutboundMessageStore` and `SubscriberStore` — minor, likely fine as-is

Both are ~10-line `Map` wrappers (`save`/`find`/`getAll`). `SubscriberStore`'s own comment already says it "mirrors" the other's pattern — this was a conscious, acknowledged repetition, not an oversight. The doc's own module boundaries (distribution vs. subscriber management are different bounded contexts) argue for keeping the classes separate; only the tiny CRUD mechanics are duplicated. Flagging as optional, not recommending action.

### L5. `unresolvedZoneSubscribers` is plumbed through but nothing acts on it operationally

`HazardWarningSystem.ingestAndProcess()` surfaces `unresolvedZoneSubscribers` in its per-alert result (correctly wired, per the subscriber-management-stage fix), but nothing logs it to the audit trail or raises it as an operational signal — it's there for a caller to notice, easy to silently ignore in practice. Not a bug; a data plumbing gap that stops short of being an operational one.

### L6. All storage is in-memory only — consistently and honestly flagged everywhere, still fully open

`AuditLog`, `OutboundMessageStore`, `SubscriberStore`, `ApprovalWorkflow`'s request map, and `DedupService`'s reading-by-event map are all plain in-process `Map`/array state. Every one of these already says, in its own comment, that a real deployment needs persistent backing. No drift, nothing hidden — "database/configuration loss" (the threat-model item) is real and currently has zero mitigation, but this was never presented as otherwise.

- Self-approval rejection checked before role eligibility, on every profile — `ApprovalWorkflow.js`, unchanged.

- `HazardWarningSystem`'s private (`#`) fields genuinely prevent external access to `NotificationService` — re-verified structurally: `Object.getOwnPropertyNames` cannot see private fields; the only public methods are the seven intended ones.

## Threat-model spot check

| Threat | Status | Where |
|---|---|---|
| Compromised admin account | **Partially mitigated** | RBAC + non-self-approval + audit log make a compromised *Administrator* still unable to unilaterally approve their own send. No MFA (explicitly deferred), no account/session/credential model at all — `Role.User` is just a role tag with no authentication behind it, so "compromised" doesn't have much to compromise yet. |
| Stolen SMS/API credential | **Not yet applicable** | No real provider/credentials exist. See M6 — nothing built in preparation either. |
| Spoofed or untrusted source feed | **Open, unmitigated** | See H3. No authentication of the ingested feed beyond trusting the configured URL. |
| Replay of an old warning | **Open, unmitigated** | No check anywhere that a fetched CAP payload isn't a stale/previously-cancelled warning being replayed by a compromised or misconfigured source — `DedupService` matches on `alert_id`/event pattern for *correlation*, not on freshness for *rejection*. |
| Malicious insider / unauthorized operator | **Best-mitigated threat in the system** | RBAC, self-approval rejection, per-profile approver requirements, rate limiting, and a tamper-evident audit log all directly target this. Still no MFA and no account provisioning/de-provisioning process. |
| Duplicate delivery from retry/failover | **Retry: mitigated. Failover: not applicable** | Idempotency covers the retry half (`notificationService.test.js`). No failover chain exists yet (explicitly deferred in an earlier stage), so that half of the threat has nothing to test against yet. |
| Corrupted boundary dataset | **Partially mitigated** | `geometry_hash` recorded for later forensic comparison; not verified against a known-good value at load time. See M5. |
| Source outage misread as "no warning" | **Open, unmitigated** | Same gap as H2/acceptance criterion #11 — this is the same finding under two different names in the doc. |
| Database/configuration loss | **Open, but honestly flagged everywhere** | All storage is in-memory; every store's own comment already says so. See L6. |

## Recommendation for next conversation

Suggest working through severity top-down: H1-H4 first (two of which — H1, H3 — are really one root gap: the ingestion boundary trusts its input completely), then decide which of M1-M7 are worth fixing now vs. deferring on purpose (some, like M6, are correctly deferred already). L1-L6 are cheap, optional cleanup whenever convenient.
